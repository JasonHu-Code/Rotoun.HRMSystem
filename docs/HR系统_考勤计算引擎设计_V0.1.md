> 编制日期：2026-10-19
> 配套：《HR系统_数据库设计_V0.1》第八、九章（考勤表）
> 覆盖需求：`HR-ATT-01`～`HR-ATT-13`、`HR-ATT-18`～`HR-ATT-29`
> 状态：**待评审**。业务规则部分需 HR 确认后才能编码。

---

## 一、定位与设计原则

考勤引擎是整个系统里唯一"算错了会直接扣钱"的模块。它的设计目标不是功能多，而是**能自证**：任何时候被问"这天为什么这么算"，都能还原出完整依据。

四条原则：

| # | 原则 | 含义 |
|---|---|---|
| 1 | **纯函数** | 输入（员工 + 日期 + 规则快照 + 班次 + 打卡 + 单据）→ 输出（日结果）。同样的输入必须得到同样的输出，可重算、可单测 |
| 2 | **原始数据只读** | 引擎不修改打卡流水。补卡、申诉、调整都是独立单据，引擎读的是"有效单据集合" |
| 3 | **计算留痕** | 结果存 `rule_version` / `calendar_version` / `calc_batch_no`。规则改了不回溯已锁定月份 |
| 4 | **确定性优先于灵活性** | 宁可少几个配置项，也不要出现"同样情况两个人算出不同结果" |

---

## 二、输入与输出

### 2.1 输入

| 输入 | 来源表 | 说明 |
|---|---|---|
| 员工与当前任职 | `employee` / `employment` | 确定法人、组织、用工性质 |
| 考勤规则 | `attendance_rule` | **按继承链解析**，不是简单取值 |
| 工作日历 | `work_calendar` | 当天法定属性：工作日 / 休息日 / 法定节假日 |
| 个人日历覆盖 | `work_calendar_override` | 是否被单独安排上班 |
| 排班 | `shift_schedule` | 当天班次；无排班则为空 |
| 班次定义 | `shift` / `shift_segment` | 时段、跨天、容差、弹性 |
| 个人长期班次 | `employee_shift_binding` | 无排班时的兜底班次 |
| 打卡流水 | `attendance_punch_raw` | 只读，按时间窗取 |
| 单据 | `leave_apply` / `overtime_apply` / `attendance_appeal` / `attendance_adjust_order` | 只取审批通过且生效的 |

### 2.2 输出

写 `attendance_day_result` 一条记录，字段见数据库设计 8.11。核心输出：

- 应出勤分钟、实际出勤分钟、迟到/早退分钟、缺勤分钟、缺卡次数
- 三档加班分钟（工作日 / 休息日 / 法定节假日）
- 请假分钟
- 当日状态（正常 / 异常 / 请假 / 休息 / 法定假）

## 三、总体流程（七步）

顺序不能换。**先定"该不该来"，再算"来没来"，最后算"多待了多久"**。

```
① 定上下文   员工 → 法人/组织 → 解析规则 → 取日历
② 定应出勤   日历属性 + 排班 + 个人覆盖 → 应出勤？计划加班？
③ 定时段     班次时段展开（多段班、跨天）
④ 打卡配对   原始流水 → 上班卡/下班卡配对
⑤ 单据冲抵   请假、出差、公出占用时段
⑥ 异常判定   迟到、早退、缺卡、旷工
⑦ 加班认定   实际超出应出勤的部分，按日切分 × 倍率
```

## 四、规则继承链解析

对应 `HR-ATT-19`。这是引擎的地基，必须单测覆盖。

### 4.1 解析顺序

```
EMPLOYEE（个人）
  ↓ 未命中
TEAM（班组）
  ↓ 未命中
DEPARTMENT（部门）
  ↓ 未命中
COMPANY（公司/法人）
  ↓ 未命中
GROUP（集团默认，必须有且仅有一条）
```

**取第一个命中的整条规则，不做字段级合并。**

这一点必须明确：如果做成"个人配了迟到容差、公司配了加班倍率，两者拼起来"，规则数量一多就无法解释某条结果是怎么来的。整条命中，来源唯一，可追溯。

### 4.2 命中条件

```sql
select * from attendance_rule
where is_deleted = 0
  and is_enabled = 1
  and scope_type = #{scopeType}
  and scope_id = #{scopeId}
  and effective_from <= #{date}
  and effective_to >= #{date}
order by rule_version desc
limit 1
```

### 4.3 个人级配置的约束

`scope_type='EMPLOYEE'` 的规则**不允许自由创建**，只能通过 `employee_shift_binding`（特殊工时备案）间接产生，且必须带原因类型与审批。

理由：个人自由配规则等于给考勤开后门，302 人配出几十套规则后，任何一次考勤争议都无法自证。

### 4.4 缓存

规则按 `(scopeType, scopeId, date)` 解析后缓存 10 分钟，key 含 `ruleVersion`。规则变更时主动失效。

## 五、应出勤判定矩阵（最容易做错的地方）

对应 `HR-ATT-04`。**日历属性（法定）与排班（安排）是两个独立维度**，不能合并。

### 5.1 判定表

| 日历属性 `day_type` | 是否安排上班 | 是否应出勤 | 当日性质 | 打卡了算什么 | 没打卡怎么算 |
|---|---|---|---|---|---|
| WORKDAY 工作日 | 是 | **是** | 正常出勤 | 正常出勤 | 迟到/缺卡/旷工 |
| WORKDAY 工作日 | 否 | 否 | 休息 | 加班（1.5 倍） | 不扣 |
| RESTDAY 休息日 | 是 | 否 | **计划加班** | 加班（2.0 倍） | **不扣** |
| RESTDAY 休息日 | 否 | 否 | 休息 | 加班（2.0 倍） | 不扣 |
| HOLIDAY 法定节假日 | 是 | 否 | **计划加班** | 加班（3.0 倍） | **不扣** |
| HOLIDAY 法定节假日 | 否 | 否 | 法定假 | 加班（3.0 倍） | 不扣 |

### 5.2 三条硬结论

**结论一：非工作日"安排了上班"不等于"应出勤"。**

安排了但没来，**不能算旷工、不能扣钱**。他只是没来加班。很多考勤系统在这里做错——把"排了班没打卡"一律记旷工，休息日排班就变成了变相强制加班，劳动仲裁必输。

**结论二：法定节假日即使安排了上班，没来也不扣。**

法定假日休息是法定权利。安排了上班是"希望他来加班"，来不来是员工选择（除非有特殊工时批文）。

**结论三：倍率只由 `day_type` 决定，不由"是否排班"决定。**

判断顺序永远是：先看 `work_calendar` 给的是什么日，再决定 1.5 / 2.0 / 3.0。

### 5.3 应出勤时段 vs 计划加班时段

```
应出勤时段 = 班次时段   （仅当 day_type = WORKDAY 且 is_arranged = 1）
计划加班时段 = 班次时段 （仅当 day_type ≠ WORKDAY 且 is_arranged = 1）
```

两者的区别只在于**没来时的处理**：应出勤没来要扣，计划加班没来不扣。

### 5.4 工作日历的版本选取

`work_calendar` 的唯一键是 `(legal_entity_id, calendar_date, calendar_version)`，同一天允许多个版本。计算时按下面规则取：

```
取该法人、该日期下 calendar_version 最大的那条记录
并把取到的 calendar_version 写入 attendance_day_result.calendar_version
```

**为什么允许多版本**：法定节假日安排会被临时调整（比如国务院临时通知）。调整时 HR 新建 `version + 1` 的记录覆盖，旧版本保留不删。

**为什么不覆盖旧版本**：已结算月份不重算，旧结果里的 `calendar_version` 仍指向旧版本。如果打补丁式地改原记录，历史结果就说不清当时用的是哪版日历。

### 5.5 `is_arranged` 的完整计算（漏了会全天不计考勤）

```
hasSchedule    = 当日有 shift_schedule 且 !is_rest
hasBoundShift  = 当日无排班，但存在生效中的 employee_shift_binding
isArranged     = hasSchedule or hasBoundShift
```

**关键**：不能只看排班表。有个人班次绑定（哺乳期、驻外、值班岗）但没排班记录的人，`is_arranged` 必须为 1，否则这个人明明该上班，却全程按"不需要出勤"计算，一天都记不上考勤。

## 六、班次时段展开

### 6.1 单段班

```
班次：白班 08:00–17:00，休息 60 分钟
展开：[(08:00, 17:00)]，有效工时 = 9h - 1h = 8h
```

### 6.2 多段班

两段班（上午/下午）在 `shift_segment` 存两行，展开为两个独立时段，**分别配对打卡**。

```
上午 08:00–12:00，下午 13:30–17:30
→ 段1 (08:00,12:00)、段2 (13:30,17:30)
→ 需要 4 次打卡，段内 2 次
```

### 6.3 跨天班（夜班）

```
班次：夜班 20:00–次日 08:00，is_cross_day=1，cross_day_rule=START_DAY
→ 归属日 = 排班日（如 10-19）
→ 实际时段 = 10-19 20:00 ~ 10-20 08:00
```

**取打卡的时间窗必须按归属日扩到次日**，不能按自然日取。否则夜班永远缺下班卡，这是考勤系统最常见的 bug。

时间窗公式：

```
归属日 D 的打卡窗口 = [D 00:00 - 12h, D 23:59 + 12h]
```

12 小时是冗余缓冲，用来兜住"提前到岗"与"延后离岗"。

## 七、打卡配对算法

### 7.1 配对规则（单段）

对一个时段 `[S, E]`：

| 打卡情况 | 配对结果 |
|---|---|
| ≥2 次 | 上班卡 = 时段内最早一次；下班卡 = 时段内最晚一次；中间打卡记为"多余打卡"，仅留审计，不参与计算 |
| 1 次 | 按就近原则判定：距 S 更近 → 上班卡（缺下班卡）；距 E 更近 → 下班卡（缺上班卡） |
| 0 次 | 无卡（缺勤候选，需结合单据判断） |

**为什么"取最早 + 最晚"而不是"取最接近上下班时间的"**：员工可能提前 40 分钟到岗，也可能下班后又待了一小时。取最早/最晚更接近真实在岗时长，也更容易解释。代价是可能多算加班，所以加班认定环节还有单据约束（见第九节）。

### 7.2 多段班

每段独立配对。段与段之间的打卡属于"段间外出"，不计入工时，但记录下来供"中途外出"场景核对。

### 7.3 重复打卡与设备抖动

同一员工同一分钟内多条流水（设备重复上报、人脸识别多次）：按 `(emp_no, punch_time 精确到分钟)` 去重，保留最早一条，其余标记 `is_duplicate`。

这一步在**入原始流水时不做**，在配对时做。因为原始流水必须保持"设备报什么就存什么"。

### 7.4 未认领的流水

`is_claimed = 0` 的流水不参与任何计算，进入"待认领队列"。这对应 `HR-ATT-29` 里 `device_user_relation` 没配全的情况——先让数据进得来，再让人认领，不要因为对不上工号就拒收。

## 八、出勤时长与迟到早退

### 8.1 在岗时长

```
单段在岗分钟 = 下班卡 - 上班卡 - 班内休息分钟
```

班内休息只在**单段班且连续在岗超过阈值**时扣减。多段班的段间时间不扣（本来就没算进去）。

### 8.2 迟到

```
迟到分钟 = max(0, 上班卡时刻 - 班次上班时刻 - 迟到容差)
```

容差来源：班次层 `late_tolerance_min` 优先，为空则取规则层。**默认容差为 0**（业务口径"基本没有容差"），即 08:00 上班、08:01 打卡就算迟到 1 分钟。

**迟到不等于旷工。** 迟到只记分钟数，扣款规则在薪酬模块配（`HR-PAY-10`），考勤引擎只负责出事实。

**迟到后的补卡**：员工可提交补卡申请（每月 3 次额度），补卡填**实际到岗时间**。补卡的作用是让打卡记录完整，**不是消除迟到**——填 08:40 迟到分钟数仍是 40。虚报时间由审批人把关，系统只留痕。

### 8.3 早退

```
早退分钟 = max(0, 班次下班时刻 - 下班卡时刻 - 早退容差)
```

### 8.4 缺卡

应打卡次数（`shift.punch_count`）与实际配对数之差。缺卡只记次数，**不直接判旷工**。

### 8.5 旷工

必须同时满足三个条件才判旷工：

1. 当日 `day_type = WORKDAY` 且 `is_arranged = 1`（应出勤）
2. **当日零次打卡**，或实际出勤时长 < 旷工阈值（`absent_threshold_min`，默认 240 分钟）
3. **无任何有效单据解释**（无请假、无出差、无审批通过的补卡申诉）

三个条件缺一，只能记异常，不能记旷工。

#### 缺卡与旷工的优先级（关键）

"有没有卡"的判断**优先于**"时长够不够"。判定顺序：

| 打卡情况 | 判定 | 说明 |
|---|---|---|
| **0 次打卡** + 应出勤 + 无单据 | `ABSENT` 旷工 | 完全没来 |
| **1 次打卡**（缺 1 次） | `MISSING` 缺卡，**不判旷工** | 可能是忘打下班卡，走补卡流程 |
| ≥2 次但时长不足阈值 | 按时长判 `LATE` / `EARLY` / `ABSENT` | 有完整在岗记录，时长可信 |

**为什么这条要单独写**：如果只按"时长 < 240 分钟"判旷工，那么"只打了上班卡、忘打下班卡"的员工会被判旷工并扣款。这是考勤争议的第一大来源——员工确实来上班了，只是忘了打卡。缺卡是流程问题，旷工是纪律问题，两者不能混。

**零次打卡直接判旷工**（业务已确认）。不设待定状态，判定依据见第十一节 11.2。判定后员工可在申诉受理期内提出异议，申诉通过则重算。

## 九、单据冲抵

### 9.1 冲抵优先级

```
① 出差/公出（视同出勤，最高优先）
② 请假（占用时段，不要求打卡）
③ 补卡申诉（补充缺失的打卡）
④ 考勤调整单（仅对已锁定月份的更正）
```

**顺序不能乱**：同一天既有出差又有请假时，先按出差覆盖的时段扣掉，剩下的时段才允许请假占用。反过来会重复冲抵。

### 9.2 半天假的处理

上午请假 → 只要求下午时段打卡，上午时段按请假计入 `leave_minutes`，不计缺卡。

不需要"半天假专用逻辑"，靠时段重叠计算即可：请假时段 `[08:00, 12:00]` 与段1 完全重叠 → 段1 不要求打卡。

### 9.3 请假与加班冲突

请假时段内不产生加班。即使员工来了，也按请假处理，不算加班——否则可以"请年假同时领加班费"。

## 十、加班认定

对应 `HR-ATT-10`。这是最容易算错钱的地方。

### 10.0 申请时点：事后申请

业务口径是**先加班、后填报**：员工实际加完班，再提交加班单，审批通过后认定。

这对引擎的影响：

- 日结果里记录的**实际加班分钟**是物理事实，照算不误，不等审批
- **认定加班分钟**需要审批单支撑，没有单子的部分只记"未申请加班"
- 因为申请在事后，**不存在"申请了但没来加班"**的场景，简化了比对逻辑（只需取小，不需处理"申请量大于实际"之外的情况）

### 10.1 认定公式

```
实际加班分钟 = 在岗时间 - 应出勤时段重叠部分
认定加班分钟 = min(实际加班分钟, 审批通过的加班分钟)
```

- 规则 `overtime_need_apply = 1` 时，**没有审批通过的加班单，一律不认定**，只记 `OVERTIME_NO_APPLY` 提示。
- 规则 `overtime_need_apply = 0` 时，按实际加班计算。

### 10.2 加班必须按"日"切分，不能按起始日一刀切

这是最关键的一条。

**错误做法**：按加班的开始日期取倍率。

```
周五 22:00 到周六 02:00 加班 → 全按工作日 1.5 倍  ← 错
```

**正确做法**：把加班时段按自然日切开，每段按所在日的 `day_type` 取倍率。

```
周五 22:00–24:00 → 2h × 1.5 倍
周六 00:00–02:00 → 2h × 2.0 倍
```

如果不切分，跨法定节假日的加班会被系统性少算，员工一旦发现就是集体争议。

### 10.3 三档倍率

| `day_type` | 倍率字段 | 默认值 |
|---|---|---|
| WORKDAY | `workday_overtime_rate` | 1.5 |
| RESTDAY | `restday_overtime_rate` | 2.0 |
| HOLIDAY | `holiday_overtime_rate` | 3.0 |

**倍率只从规则取，不允许在薪资模块另配一套。** 薪资模块引用考勤结果的三档分钟数，不再自行判断日期类型。

### 10.4 加班最小单位：1 小时

业务口径是**小时**。`overtime_round_unit_min = 60`，`overtime_round_type = CEIL`（向上取整）。

```
实际加班 8 分钟  → 认定 60 分钟（1 小时）
实际加班 65 分钟 → 认定 120 分钟（2 小时）
实际加班 120 分钟 → 认定 120 分钟
```

取整方式做成可配（`CEIL` / `FLOOR` / `ROUND`），默认向上。**不要在代码里写死**——将来业务想改"不满半小时不计"，改配置即可，不用改代码。

### 10.5 月加班上限：按公司配置

`overtime_month_limit_hour` **在公司级规则里配置**，不同公司可以不同（业务明确"不同公司情况不同"）。

- 集团默认值 36 小时
- 公司级规则可以覆盖，比如某公司批了综合工时制，可以设 60
- **超过上限只预警不硬拦**。硬拦会导致超出部分不进系统，反而更难追溯
- 超限同时生成 `attendance_exception(OVERTIME_OVER_LIMIT)`，进异常台账

> 合规提醒：36 小时是《劳动法》第 41 条的法定上限。公司级配置超过 36 时，系统应给强提示并要求填写依据（如综合工时批文编号），否则一旦被劳动监察查到，系统日志会显示"企业自行配置超法定上限"，对企业不利。

### 10.6 加班转化：转工资 or 转调休

业务确认加班有两种去向，**这是本期新增的完整流程**。

#### 状态流转

```
员工加班（打卡有记录）
   ↓  事后提交加班单，选转化方式
待审批 PENDING
   ↓  审批通过
已认定（confirm_hours 确定）
   ├── settle_type = WAGE      → 进入当月薪酬计算
   └── settle_type = COMP_TIME → 生成调休额度（小时），写 leave_quota_log
                                      ↓ 员工请假使用调休
                                 已使用 USED
```

#### 与考勤引擎的边界

**引擎不负责转化**，只负责算出"实际加班分钟"和"认定加班分钟"。转化在加班单审批通过后由独立逻辑处理。

引擎输出的三档分钟数是薪酬和调休的共同数据源：

| 消费方 | 取数方式 |
|---|---|
| 薪酬模块 | 按档位取 `overtime_*_minutes` 中 `settle_type = WAGE` 的部分 |
| 调休额度 | 按档位取 `settle_type = COMP_TIME` 的小时数，写入 `leave_quota` |

#### 合规约束（必须实现）

| 加班档位 | 允许转化 | 依据 |
|---|---|---|
| `WORKDAY` | **仅 WAGE** | 延时工作必须付 1.5 倍，不可调休替代 |
| `RESTDAY` | COMP_TIME 优先，不休才付 2 倍 | 法律允许"安排补休" |
| `HOLIDAY` | **仅 WAGE** | 法定节假日必须付 3 倍 |

**跨档加班单的特殊处理**：一张单可能同时含工作日和休息日两段（如周五 22:00–周六 02:00）。这时不能用一个 `settle_type` 覆盖全单，必须**按档位拆分**：

```
工作日部分 120 min → 强制 WAGE
休息日部分 120 min → 按员工选择
```

因此实现时要注意：**薪酬取数不看单据的 `settle_type` 单值，而是看日结果的三档分钟数 + 各档的转化规则**。只看单值会算错跨档单。

#### 调休额度的有效期

调休不是永久有效。`comp_time_expire_date` 由规则配置（建议次年年末），过期作废。生成额度时写 `leave_quota_log(change_type='GRANT')`，使用时写 `USE`。

## 十一、当日状态

结果表 `attendance_day_result` 的最终状态，取值必须互斥：

| 状态 | 判定条件 | 边界说明 |
|---|---|---|
| `HOLIDAY` | `day_type = HOLIDAY` | **无论是否加班都是 HOLIDAY**。加班量看 `overtime_holiday_minutes` |
| `REST` | `day_type = RESTDAY`（含"安排了但没来"） | 是否安排了看 `is_arranged`，不新增状态值 |
| `LEAVE` | 请假时段**覆盖全部应出勤时段** | **半天假不是 LEAVE**，是 `NORMAL` + `leave_minutes > 0` |
| `TRIP` | 出差覆盖全部应出勤时段 | 半天出差同半天假的处理 |
| `NORMAL` | 应出勤且无任何异常 | |
| `ABNORMAL` | 存在迟到/早退/缺卡/**旷工**之一 | 旷工直接落这里，不设待定态 |

### 11.1 三个容易判错的边界

**① 半天假**：不置 `LEAVE`。`LEAVE` 的语义是"这天没上班"，半天假是"上了半天班"。用 `leave_minutes` 表达，状态仍是 `NORMAL`。

**② 休息日排了班没来**：置 `REST`，不置 `ABNORMAL`。想筛出这批人用 `is_arranged = 1 and status = 'REST'`。不新增 `ARRANGED_ABSENT` 之类的状态值——状态值一多，报表口径就乱。

**③ 法定节假日加班**：置 `HOLIDAY`，不置 `NORMAL`。统计"节假日加班人次"时用 `sum(overtime_holiday_minutes) > 0` 筛，而不是靠状态。

> 设计原则：**状态只表达"这天是什么性质"，不表达"干得好不好"**。加班、请假、迟到这些量化信息都在各自字段里，状态字段不承担这个职责。

### 11.2 为什么取消"待定"状态

最初设计里有个 `NO_RECORD`（应出勤但零打卡，暂不判旷工，等申诉期）。业务确认后**取消**，理由：

1. **业务口径明确要求"旷工直接记旷工"**。留一个待定态，HR 在月底做结算时要人工处理一批"待定"，反而增加工作量。
2. **申诉是事后流程，不改变初始判定**。判了旷工、员工有异议就申诉，申诉通过后重算。这个顺序比"先不判、等申诉"更清楚。
3. **设备故障由运维兜底**。设备掉线导致全员零打卡，属于设备监控告警的职责（`HR-DEV-12`），不该让考勤引擎承担这个模糊地带。

因此：`status` 只有六个值，旷工归 `ABNORMAL`，`absent_type = ABSENT`。申诉受理期（`appeal_window_days`）仍然保留，但语义变为"超过该期限不再受理申诉"。

## 十二、重算与快照

### 12.1 触发重算的七种情况

| 触发源 | 影响范围 |
|---|---|
| 补卡申诉审批通过 | 该员工该日 |
| 请假单审批通过/撤销 | 请假区间内所有日 |
| 加班单审批通过/撤销 | 加班跨度的所有日 |
| 排班变更 | 被改动的员工日期 |
| 组织/职位调整 | 生效日之后的日期 |
| 规则变更 | 生效日起、**未锁定月份** |
| 月度结算前全量重算 | 当月全量 |

### 12.2 重算规则

- 已锁定月份**禁止自动重算**，只能通过 `attendance_adjust_order` 逐条调整
- 每次重算生成新的 `calc_batch_no`，结果覆盖写，但批次号变更可追溯
- 重算必须是幂等的：同一输入重复跑，结果完全一致

### 12.3 为什么日结果要存版本快照

规则变了，"10 月 8 日迟到 5 分钟算不算迟到"这个判断依据就变了。存下 `rule_version` 和 `calendar_version`，才能回答"当时是按哪版规则算的"。

只存 `rule_id` 不够——规则内容可以被改，ID 不变。

## 十三、核心伪代码

```
function calcDay(empId, workDate):
    # ① 上下文
    emp      = loadEmployee(empId)
    org      = loadOrgAt(empId, workDate)            # 由 employment 区间确定
    rule     = resolveRule(empId, org, workDate)     # 继承链，返回唯一一条
    calendar = loadCalendar(emp.legalEntityId, workDate)  # 取 calendar_version 最大的一版
    schedule = loadSchedule(empId, workDate)              # 可能为空
    bound    = loadBoundShift(empId, workDate)            # 个人长期班次，可能为空
    shift    = schedule?.shift ?? bound
    docs     = loadValidDocs(empId, workDate)             # 只要审批通过的

    # ② 应出勤判定（见第五节矩阵）
    dayType    = calendar.dayType                     # WORKDAY / RESTDAY / HOLIDAY
    isArranged = (schedule != null and !schedule.isRest) or bound != null   # 见 5.5
    required   = (dayType == WORKDAY and isArranged)

    # ③ 时段展开
    segments = required || isArranged ? expandSegments(shift, workDate) : []
    requiredMinutes = required ? sum(segments, rule) : 0

    # ④ 打卡配对（时间窗按归属日扩 12 小时）
    punches = loadPunches(empId, workDate - 12h, workDate + 36h)
    pairs   = pairPunches(punches, segments)

    # ⑤ 单据冲抵
    leaveMinutes = overlapMinutes(docs.leaves, segments)
    tripMinutes  = overlapMinutes(docs.trips,  segments)

    # ⑥ 异常判定
    lateMinutes  = calcLate(pairs, segments, rule)
    earlyMinutes = calcEarly(pairs, segments, rule)
    missingCount = required ? (shift.punchCount - pairs.size) : 0
    workedMinutes = sum(pairs.duration) - leaveMinutes - tripMinutes

    absentMinutes = max(0, requiredMinutes - workedMinutes - leaveMinutes - tripMinutes)

    # 旷工三条件（缺一不可）
    isAbsent = required
               and absentMinutes >= rule.absentThresholdMin
               and leaveMinutes + tripMinutes == 0
               and !docs.hasApprovedAppeal(workDate)

    # ⑦ 加班（按自然日切分，逐段取倍率）
    otSegments  = subtract(pairs.actualRanges, requiredRanges)
    otSplit     = splitByNaturalDay(otSegments)        # 关键：跨零点拆分
    otWorkday   = sumRate(otSplit, WORKDAY)
    otRestday   = sumRate(otSplit, RESTDAY)
    otHoliday   = sumRate(otSplit, HOLIDAY)

    # 有申请才认定
    if rule.overtimeNeedApply:
        otWorkday = min(otWorkday, docs.approvedOT(WORKDAY))
        otRestday = min(otRestday, docs.approvedOT(RESTDAY))
        otHoliday = min(otHoliday, docs.approvedOT(HOLIDAY))

    # ⑧ 落库（upsert，带版本快照）
    return {
        empId, workDate,
        shiftId: shift?.id, ruleId: rule.id,
        ruleVersion: rule.version, calendarVersion: calendar.version,
        dayType, isArranged, required,
        requiredMinutes, workedMinutes, lateMinutes, earlyMinutes,
        absentMinutes, absentType: classify(...), missingCount,
        otWorkday, otRestday, otHoliday, leaveMinutes,
        status: decideStatus(...),
        calcBatchNo
    }
```

### 15.1 加班两种转化的合规约束（必须实现）

劳动法第 44 条规定了不同情形的处理方式，系统必须按档位限制转化方式，不能一律允许调休：

| 加班档位 | 允许的转化方式 | 理由 |
|---|---|---|
| `WORKDAY` 工作日延时 | **仅 `WAGE`** | 延长工作时间必须付 1.5 倍工资，不能用调休替代 |
| `RESTDAY` 休息日 | `COMP_TIME` **优先**，不休才付 2 倍 | 法律允许"安排补休"，补休后不再付加班费 |
| `HOLIDAY` 法定节假日 | **仅 `WAGE`** | 法定节假日必须付 3 倍工资，不可用调休替代 |

**提交校验**：`settle_type = COMP_TIME` 且 `overtime_kind` 为 `WORKDAY` 或 `HOLIDAY` 时，直接拒绝，返回 `14007 该加班档位不可转调休`。

**跨档加班**（如周五 22:00 到周六 02:00）会拆成两段不同档位，因此**一张加班单可能同时存在只能转工资和可以转调休的部分**。处理方式：跨档单的 `settle_type` 由系统按档位自动拆分——
- 工作日/节假日部分：强制 `WAGE`
- 休息日部分：按员工选择 `WAGE` 或 `COMP_TIME`

为此 `attendance_day_result` 的三档加班分钟数才是真正的计算依据，**薪酬模块按档位取数，不看单据的 `settle_type` 单值**。这一点必须在实现时注意，否则跨档单会算错。

### 15.2 补卡与迟到的关系（需要业务再确认一次）

业务原话是"迟到后申请补卡，一个月三次补卡机会"。这里有个隐含风险要说清：

补卡填的是**实际到岗时间**。如果员工迟到 40 分钟，补卡填 08:40，那迟到分钟数仍是 40 —— 补卡只是让打卡记录完整，**不能消除迟到**。

但如果员工填 08:00（谎报），迟到就消失了。系统层面无法判断真假，只能靠**审批人把关 + 全程留痕**。

建议产品上加两条约束：
1. 补卡申请页明确提示"请填写实际到岗时间，虚报将按违纪处理"
2. 补卡审批通过后，若补卡时间与班次上班时间完全一致且当月已有 2 次以上，在 HR 端标黄提示"高频准时补卡"

这两条不写进需求清单，属产品体验优化，但能显著降低滥用。

## 十六、性能与实现建议

### 16.1 数据量估算

302 人 × 30 天 ≈ **9,060 条日结果/月**，约 11 万条/年。打卡流水约 22 万条/年。

**这个量级单机 MySQL 完全够用，不需要分库分表、不需要分布式计算。** 不要为了"看起来专业"上大数据组件。

### 16.2 计算模式

| 模式 | 说明 | 用途 |
|---|---|---|
| 增量计算 | 单据审批通过后，只重算受影响的员工日期 | 日常 |
| 全量重算 | 月度结算前，按公司+月份全量 | 月结 |
| 试算 | 不落库，直接返回结果 | HR 核对 |

单次全量重算 9,060 条约 3–10 秒（含打卡配对），可以同步执行，不需要异步任务框架。

### 16.3 建议的代码结构

```
attendance-engine/
├── resolver/     规则继承链解析、日历合并
├── puncher/      打卡配对（纯函数，最需要单测）
├── calculator/   出勤、异常、加班计算
├── docfilter/    单据有效性过滤与时段裁剪
└── facade/       calcDay / recalcRange / recalcBatch
```

**`puncher` 与 `calculator` 必须是纯函数，不碰数据库。** 数据由 facade 一次性装配好传进去。这样 20 个边界场景可以直接用内存数据写单测，不用起数据库。
